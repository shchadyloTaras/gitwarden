## Broken (with root cause, each confirmed by minimal repro)

1. **Wrong-author commits are allowed and pushed — the app's core promise fails at the gate.**
   `EMAIL_MISMATCH` is classified `'warning'` (`src/core/safety/safetyMessages.ts:9`), so with
   `user.email = marketing@eleken.co` vs profile `tarasdidg@gmail.com` the Commit button stays
   enabled (soft ⚠ only) and the push sheet still says "✓ Identity check passed — safe to push"
   (it checks current config + token account, never the authorship of the outgoing range).
   Proven live: commit `97a09a9` authored `eleken-git <marketing@eleken.co>` was created via the
   UI and **pushed to the real GitHub repo**. Safety Center simultaneously reports the mismatch
   issue and "Can commit ✓ Yes". (The wrong-author commit is still on `shchadyloTaras/test` if you
   want to clean it.)
2. **No author-NAME check exists at all** (2026-07-08 bug #5, still present). Only email is
   compared; the safety catalog has no `NAME_MISMATCH` code. Repro: `user.name = eleken-git`,
   correct email → zero flags anywhere, Guard "Ready".
3. **Secret scan never runs at the commit gate** (bug #4, still present). `STAGED_SECRET_DETECTED`
   is catalogued as a **blocker** but nothing deterministic emits it — it exists only in the type
   union and the AI copilot mapping. Repro: staged a file with an AWS key pair + GitHub PAT →
   commit enabled, no flag. The deterministic pattern detector demonstrably exists (its finding
   shows up inside AI `/review`) — it is just not wired into the guard.
4. **`.git/HEAD` and `.git/index` file watchers die after the first git write** (bug #1, still
   present, sharpened). `fs.watch` on a _file_ follows the inode; git updates HEAD/index via
   `*.lock` + `rename()`. Minimal Node repro: 3 rename-replacements → 1 event. In-app: external
   `checkout -b` switches keep being detected (the recursive `refs/` _directory_ watch masks the
   death), but plain `git checkout <existing-branch>` — the most common case — is missed from the
   second HEAD write onward (repro: 3 switches, third one invisible until an unrelated refs event).
   Fix direction: watch the `.git` directory (non-recursive) instead of the files.
5. **Transient outcome banners are wiped by the app's own watcher-triggered refresh** (bug #2, now
   understood as systemic). `loadBranches()` resets `switchError`/`mergeConflict`/`successMessage`
   (`branchStore.ts:93`) and `remoteStore.load()` resets `lastFailure`; the watcher's
   `refreshActiveRepo('full')` fires ~400 ms after any operation that touches `.git` — including
   the operation whose outcome the banner reports. Deterministic worst case: a **failed pull's
   banner is always wiped on the first attempt** (the pull's own fetch phase updates
   `origin/main` → refs event → wipe) and only survives on retry (no-op fetch, no event). Observed
   live both ways, 30 s apart. Same mechanism silently discards the "Bring changes & switch"
   pop-conflict outcome (user lands on Status with bare `!` rows and an **orphaned stash entry**
   the app never shows) and usually eats push/merge success toasts.
6. **`/push-brief` misreports the trust-critical fact.** With a working OAuth token it appends
   "GitHub HTTPS: no stored token for the assigned profile." Root cause: the chat command builds
   `PushBriefPayload` without the `github` block (`aiChatStore.ts:459`), and the service defaults
   `hasToken: false` (`PushBriefService.ts:67`). The push sheet computes the same fact correctly.
7. **`/propose` still accepts an empty edit set as success** (bug #3, code path unchanged —
   `Applied ${writtenFiles.length} file edit(s)` renders "Applied 0 file edit(s)" and marks the
   proposal applied). Positive path works (applied a real edit this run).
8. **Dirty-switch failure is mapped to "An unexpected Git error occurred."** ErrorMapper has no
   pattern for git's "Your local changes … would be overwritten by checkout"; it falls through to
   `unknown`. The banner's remediation button is right; the explanation is wrong.
9. **Stability watch-item (unconfirmed):** one full-app exit ~0.7 s after the first AI connection
   save (connection persisted fine; relaunch stable; no crash report; the only `app.quit()` in the
   codebase is the non-darwin `window-all-closed` handler), plus one earlier renderer/CDP loss
   under the harness. Neither reproduced. Worth keeping an eye on `render-process-gone` /
   `child-process-gone` telemetry — the app currently subscribes to neither.

## Confusing (UX notes, first-time-user perspective)

- **No clone-from-URL.** Add Repository takes a local path only — a first-time user whose repo
  lives on GitHub cannot get it into the app without the terminal. The tour even says "Add an
  existing local repository" as if the terminal step is assumed.
- **Guard badge freshness.** The badge said "Ready" while the Commit screen showed the mismatch
  warning, and during an unresolved merge conflict; it catches up only when some screen recomputes.
  Also `.git/config` isn't watched at all — external identity changes (the app's core concern) go
  unnoticed until a screen revisit.
- "Merge commits can't be returned this way." floats context-free above the History table — it's
  the uncommit refusal, but nothing labels the panel as the uncommit feature.
- During a conflict, Commit shows "There are no staged changes to commit" while Status lists the
  conflicted file under "STAGED CHANGES (1)", and two identical "Go to Status →" links render.
- Push sheet's "✓ Identity check passed — safe to push" reads as an authorship guarantee but never
  inspects the outgoing commits (see Broken #1).
- Enter doesn't send a slash command typed in one go (the suggestion popup appears to swallow the
  first Enter); the send button works. Plain messages send with Enter fine.
- The Pull button's tooltip can linger detached mid-screen after a click (cosmetic).
- After Initialize, the app lands on the Commit screen showing two ⛔ blockers; Status (to stage
  the first files) would be the natural landing.
- DX note (repo tooling, not the app): `commit-needs-log.sh`'s documented bypass
  (`GITWARDEN_SKIP_LOG_GATE=1 git commit …`) can never work when the hook runs — the hook checks
  its **own** process env, which an env prefix on the user's command line never reaches.

## Suggested priorities

1. Broken #1–#3 are one product decision + small wiring: add `NAME_MISMATCH`, wire the existing
   secret detector into the commit gate, and either promote `EMAIL_MISMATCH` to blocker (with the
   one-click fix right there) or check outgoing authorship at push.
2. Broken #4+#5 share one theme — the freshness system undermines itself. Watch the `.git` dir
   (+ `config`), and stop full-resetting transient banner state on refresh (keep operation outcomes
   in state the loaders don't own).
3. #6–#8 are small, well-localized fixes.
