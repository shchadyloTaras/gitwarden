Whole-app, first-time-user pass of the real GitWarden build (HEAD `a4d1f1a`) against the real
`github.com/shchadyloTaras/test` repo, a real GitHub OAuth device-flow authorization (completed by

## What works (verified end-to-end)

- **Onboarding**: 12-step tour auto-opens on true first launch, sensible anchors, replayable from
  Settings → Walkthrough.
- **Profiles + GitHub OAuth**: device flow shows the code, opens the browser, polls, auto-fills
  identity (`Taras Shchadylo <tarasdidg@gmail.com>`, `@shchadyloTaras`), reconnect/disconnect;
  survives restart.
- **Repositories**: add-by-path with validation; profile assignment **auto-writes local git
  identity** (`applyAssignedProfileIdentity`) — nice safety-by-default; notes; remove-from-app
  (keeps folder); non-repo path → **Initialize** flow (init on `main`, identity auto-set, repo
  auto-assigned).
- **Status/diff/commit**: three-section status, live external working-tree change pickup, diff
  viewer (staged/unstaged), stage/unstage/discard, untracked delete behind a strong
  "cannot be recovered" confirm, commit blockers (nothing staged / empty message / conflicts).
- **Guard quick-fix**: email-mismatch warning on Commit offers one-click "Set local identity …"
  (local-only) — works.
- **Branches**: create & switch, per-row switch/delete/merge, header picker, fast-forward and true
  two-parent merge commits, conflict → banner + "Go to Status" + `HAS_CONFLICTS` commit blocker,
  post-resolve merge commit; **safe delete** (merged = simple confirm; unmerged = escalated
  "commits exist nowhere else — Force delete"); dirty-switch refusal with **"Bring changes &
  switch"** (stash → switch → pop).
- **History / uncommit**: table with Unpushed chips and true authors; "Return last commit" restores
  changes to the working tree intact; merge commits correctly refused.
- **Remote vs real GitHub**: fetch / pull / push over the OAuth token ("Pushing as @shchadyloTaras
  via HTTPS token ✓"); rich push confirmation sheet; **push policy** gates all verified — protected
  branch, expected-owner mismatch, and Branch-Scoped mode each hard-block with the Confirm button
  disabled; diverged-branch flow: push rejected with clear copy → pull (`--ff-only`) surfaces
  "Bring in origin/main" remediation → local merge (incl. conflicted variant routed to Status) →
  push succeeds.
- **AI (LM Studio)**: `sk-lm-` key detected (base URL pre-filled `localhost:1234/v1`), connection
  saved encrypted, models fetched, default model set; repo-aware chat; `/commit` (structured
  block + Insert → prefills Commit screen); `/review` (deterministic secret-pattern finding + AI
  findings); `/propose` (proposal preview → Apply → real file edit); `/explain` (graceful empty
  case + per-code explanation with deterministic "Suggested:" action); `/push-brief`, `/history`,
  `/repo-brief` reachable as chat commands; Settings → AI Assistant (masked key, change key, model
  picker, delete).
- **Safety Center**: full audit (identity with `(local)` source tags, remote & branch, branch
  access, verdicts + issues); updates on screen revisit; badge deep-links.
- **App shell**: persistence across restart (profiles, repos, OAuth link, AI connection), update
  check ("You're on the latest version"), custom git path validation, appearance modes.

## Broken (with root cause, each confirmed by minimal repro)

> **Status update (QA Fixes track, Phases 98–105, 2026-07-12):** all 9 items below are fixed.
> Each is annotated with the phase that closed it; the regression sweep at the end of Phase 105
> re-ran the full Vitest + Playwright suites green, including the specs written to prove each fix.

1. **Wrong-author commits are allowed and pushed — the app's core promise fails at the gate.**
   `EMAIL_MISMATCH` is classified `'warning'` (`src/core/safety/safetyMessages.ts:9`), so with
   `user.email = marketing@eleken.co` vs profile `tarasdidg@gmail.com` the Commit button stays
   enabled (soft ⚠ only) and the push sheet still says "✓ Identity check passed — safe to push"
   (it checks current config + token account, never the authorship of the outgoing range).
   Proven live: commit `97a09a9` authored `eleken-git <marketing@eleken.co>` was created via the
   UI and **pushed to the real GitHub repo**. Safety Center simultaneously reports the mismatch
   issue and "Can commit ✓ Yes". (The wrong-author commit is still on `shchadyloTaras/test` if you
   want to clean it.)
   > **Fixed by Phase 98** (`EMAIL_MISMATCH` promoted to a blocker) **+ Phase 100** (push
   > additionally verifies the outgoing commit range's authorship — `OUTGOING_WRONG_AUTHOR` — so a
   > wrong-author commit already made can't ship even after the local config is fixed). Proven by
   > `tests/e2e/wrong-author-push.spec.ts`, which reproduces the exact `97a09a9` scenario end to end.
2. **No author-NAME check exists at all** (2026-07-08 bug #5, still present). Only email is
   compared; the safety catalog has no `NAME_MISMATCH` code. Repro: `user.name = eleken-git`,
   correct email → zero flags anywhere, Guard "Ready".
   > **Fixed by Phase 98** — added `NAME_MISMATCH` to `SafetyCode`, comparing
   > `identity.userName` against `activeProfile.gitAuthorName`.
3. **Secret scan never runs at the commit gate** (bug #4, still present). `STAGED_SECRET_DETECTED`
   is catalogued as a **blocker** but nothing deterministic emits it — it exists only in the type
   union and the AI copilot mapping. Repro: staged a file with an AWS key pair + GitHub PAT →
   commit enabled, no flag. The deterministic pattern detector demonstrably exists (its finding
   shows up inside AI `/review`) — it is just not wired into the guard.
   > **Fixed by Phase 99** — the existing deterministic secret scanner is now wired into
   > `checkCommit` via a bulk staged-diffs IPC channel; a staged secret blocks commit independent
   > of any AI connection (confirmed by `tests/e2e/ai-change-review.spec.ts`, updated this phase —
   > it previously asserted the OLD, pre-fix "does not block commit" behavior).
4. **`.git/HEAD` and `.git/index` file watchers die after the first git write** (bug #1, still
   present, sharpened). `fs.watch` on a _file_ follows the inode; git updates HEAD/index via
   `*.lock` + `rename()`. Minimal Node repro: 3 rename-replacements → 1 event. In-app: external
   `checkout -b` switches keep being detected (the recursive `refs/` _directory_ watch masks the
   death), but plain `git checkout <existing-branch>` — the most common case — is missed from the
   second HEAD write onward (repro: 3 switches, third one invisible until an unrelated refs event).
   Fix direction: watch the `.git` directory (non-recursive) instead of the files.
   > **Fixed by Phase 101** — replaced the two per-file `fs.watch` calls with one non-recursive
   > `.git` directory watch (`watchGitDirTopLevel`), rename-proof by construction; also added
   > `config` to the watched/reported change kinds (closing the related "external identity changes
   > go unnoticed" note below).
5. **Transient outcome banners are wiped by the app's own watcher-triggered refresh** (bug #2, now
   understood as systemic). `loadBranches()` resets `switchError`/`mergeConflict`/`successMessage`
   (`branchStore.ts:93`) and `remoteStore.load()` resets `lastFailure`; the watcher's
   `refreshActiveRepo('full')` fires ~400 ms after any operation that touches `.git` — including
   the operation whose outcome the banner reports. Deterministic worst case: a **failed pull's
   banner is always wiped on the first attempt** (the pull's own fetch phase updates
   `origin/main` → refs event → wipe) and only survives on retry (no-op fetch, no event). Observed
   live both ways, 30 s apart. Same mechanism silently discards the "Bring changes & switch"
   pop-conflict outcome (user lands on Status with bare `!` rows and an **orphaned stash entry**
   the app never shows) and usually eats push/merge success toasts.
   > **Fixed by Phase 102** — `load()` in `remoteStore`/`branchStore`/`commitStore`/`historyStore`
   > now only resets operation-outcome fields on an actual repo change, not a same-repo refresh; a
   > new `stashPopConflict` field (split from `switchError`) gets its own persistent Status banner
   > naming the kept stash, closing the "orphaned stash the app never shows" gap.
6. **`/push-brief` misreports the trust-critical fact.** With a working OAuth token it appends
   "GitHub HTTPS: no stored token for the assigned profile." Root cause: the chat command builds
   `PushBriefPayload` without the `github` block (`aiChatStore.ts:459`), and the service defaults
   `hasToken: false` (`PushBriefService.ts:67`). The push sheet computes the same fact correctly.
   > **Fixed by Phase 104** — `PushBriefService` now resolves real token facts via the GitHub auth
   > coordinator when the caller omits the `github` block, instead of defaulting to `false`.
7. **`/propose` still accepts an empty edit set as success** (bug #3, code path unchanged —
   `Applied ${writtenFiles.length} file edit(s)` renders "Applied 0 file edit(s)" and marks the
   proposal applied). Positive path works (applied a real edit this run).
   > **Fixed by Phase 104** — an empty proposal now refuses at both render time (no Apply button)
   > and execute time (`AgenticActionExecutor` throws before doing any work), so "Applied 0 file
   > edit(s)" can no longer be reported as success.
8. **Dirty-switch failure is mapped to "An unexpected Git error occurred."** ErrorMapper has no
   pattern for git's "Your local changes … would be overwritten by checkout"; it falls through to
   `unknown`. The banner's remediation button is right; the explanation is wrong.
   > **Fixed by Phase 103** — added a `localChangesWouldBeOverwritten` `ErrorMapper` pattern (plus
   > `noCredentialsAvailable`, closing the related HTTPS-without-a-token honesty gap noted under
   > "Confusing" below) so the banner's explanation now matches its (already-correct) fix button.
9. **Stability watch-item (unconfirmed):** one full-app exit ~0.7 s after the first AI connection
   save (connection persisted fine; relaunch stable; no crash report; the only `app.quit()` in the
   codebase is the non-darwin `window-all-closed` handler), plus one earlier renderer/CDP loss
   under the harness. Neither reproduced. Worth keeping an eye on `render-process-gone` /
   `child-process-gone` telemetry — the app currently subscribes to neither.
   > **Addressed by Phase 105** — the app now subscribes to both `render-process-gone` (per window)
   > and `child-process-gone` (app-level), logging reason/exit code via the existing `Logger` (no
   > secrets). The original exit was never reproduced, so this closes the observability gap rather
   > than a confirmed root cause — if it recurs, these logs should show it.

## Confusing (UX notes, first-time-user perspective)

- **No clone-from-URL.** Add Repository takes a local path only — a first-time user whose repo
  lives on GitHub cannot get it into the app without the terminal. The tour even says "Add an
  existing local repository" as if the terminal step is assumed.
  > **Still open** — a feature request, not a bug; out of this track's scope (no phase addressed it).
- **Guard badge freshness.** The badge said "Ready" while the Commit screen showed the mismatch
  warning, and during an unresolved merge conflict; it catches up only when some screen recomputes.
  Also `.git/config` isn't watched at all — external identity changes (the app's core concern) go
  unnoticed until a screen revisit.
  > **Fixed by Phase 101** — `config` is now a watched/reported `.git` change kind, wired to the
  > same full-refresh path as `head`/`refs`, so an external identity edit updates the guard live.
- "Merge commits can't be returned this way." floats context-free above the History table — it's
  the uncommit refusal, but nothing labels the panel as the uncommit feature.
  > **Fixed by Phase 105** — the panel now has its own title ("Undo a commit (keeps your
  > changes)") above the return actions/refusal text.
- During a conflict, Commit shows "There are no staged changes to commit" while Status lists the
  conflicted file under "STAGED CHANGES (1)", and two identical "Go to Status →" links render.
  > **Still open** — not in this track's explicit Phase 105 task list; left for a future pass.
- Push sheet's "✓ Identity check passed — safe to push" reads as an authorship guarantee but never
  inspects the outgoing commits (see Broken #1).
  > **Fixed by Phase 100** — the copy (`PUSH_SAFE_TO_PUSH`) now only claims what was actually
  > checked, and Broken #1's outgoing-authorship gate means the claim is true when it does appear.
- Enter doesn't send a slash command typed in one go (the suggestion popup appears to swallow the
  first Enter); the send button works. Plain messages send with Enter fine.
  > **Fixed by Phase 105** — an exact, fully-typed command match now sends on Enter instead of
  > being re-completed by the popup; Tab still completes.
- The Pull button's tooltip can linger detached mid-screen after a click (cosmetic).
  > **Fixed by Phase 105** — `TooltipLayer` now hides a shown tooltip if its anchor disconnects
  > from the DOM, and otherwise tracks the anchor's live position while shown (rather than only
  > ever capturing it once, at show time).
- After Initialize, the app lands on the Commit screen showing two ⛔ blockers; Status (to stage
  the first files) would be the natural landing.
  > **Still open** — a landing-screen preference, not in this track's explicit Phase 105 task list.
- DX note (repo tooling, not the app): `commit-needs-log.sh`'s documented bypass
  (`GITWARDEN_SKIP_LOG_GATE=1 git commit …`) can never work when the hook runs — the hook checks
  its **own** process env, which an env prefix on the user's command line never reaches.
  > **Still open** — repo tooling, not app code; out of this track's scope.

## Suggested priorities

1. Broken #1–#3 are one product decision + small wiring: add `NAME_MISMATCH`, wire the existing
   secret detector into the commit gate, and either promote `EMAIL_MISMATCH` to blocker (with the
   one-click fix right there) or check outgoing authorship at push.
2. Broken #4+#5 share one theme — the freshness system undermines itself. Watch the `.git` dir
   (+ `config`), and stop full-resetting transient banner state on refresh (keep operation outcomes
   in state the loaders don't own).
3. #6–#8 are small, well-localized fixes.

## Phase 105 polish (not from this report, closed out alongside the sweep above)

than this QA run: staged deletions on the Commit screen now get their own icon (`D`, red) instead
